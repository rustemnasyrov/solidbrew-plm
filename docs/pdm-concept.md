# SolidBrew PDM: целевая модель

Этот документ объясняет, **как устроена** целевая PDM и почему. Что именно и в каком порядке делается, с критериями приёмки, описано в [ТЗ](pdm-spec.md). Это не перечень возможностей текущего стенда.

Предыдущая редакция: [_old/pdm-concept-2026-11-23.md](_old/pdm-concept-2026-11-23.md).

Цель — простое общее хранилище для SOLIDWORKS, КОМПАС-3D и KiCad: независимые рабочие копии у конструкторов, точные версии комплектов и никакого повторного ввода данных, которые уже есть в CAD.

## 1. Один источник для каждого вида данных

| Данные | Источник | Что делает PDM |
|---|---|---|
| Обозначение, наименование, материал и другие инженерные свойства | Свойства CAD-документа, его конфигурации или исполнения | Читает при сдаче и хранит копию для поиска. Не редактирует |
| Геометрия, вхождения, конфигурации, структура сборки, схема и плата | Сами CAD-файлы | Показывает дерево по ссылкам. Отдельный состав вручную не ведёт |
| Идентификация документа, история версий, автор и время сдачи, блокировки, журнал | БД PDM | Ведёт сама. Внутренний ID не зависит от обозначения и имени файла |
| Точные версии зависимостей опубликованного документа | БД PDM | Фиксирует при сдаче. Это не копия дерева и не спецификация |

**Пример:** сборка знает, что в ней есть `Кронштейн` и какая конфигурация используется. PDM знает, что `Рама v7` должна открываться с `Кронштейн v3`, даже если уже опубликован `v4`. Опубликованный комплект не переключается на свежие версии автоматически.

Копия свойств в БД — пересобираемый индекс для поиска, а не второй источник данных. Если свойства в файле и в индексе расходятся, прав файл.

## 2. Ядро и адаптеры CAD

Ядро PDM оперирует четырьмя понятиями: **документ, версия, зависимость, блокировка**. Оно не знает расширений файлов и не отождествляет головную сборку с `.SLDASM`.

Всё, что зависит от конкретного CAD, сосредоточено в адаптере:

- какие файлы являются документами;
- как прочитать ссылки и свойства;
- в какой версии CAD сохранён файл.

| CAD | Единица документа | Как читаются ссылки |
|---|---|---|
| SOLIDWORKS | Файл `.SLDPRT`, `.SLDASM`, `.SLDDRW` со всеми конфигурациями | API SOLIDWORKS или Document Manager API |
| КОМПАС-3D | Файл `.m3d`, `.a3d`, `.cdw`, `.spw`, `.frw` со всеми исполнениями | API КОМПАС |
| KiCad | Проект целиком: `.kicad_pro`, схемы, плата, таблицы библиотек проекта | Разбор текстовых файлов, KiCad не нужен |

Разные CAD связываются только через файлы обмена, обычно STEP. Например, STEP платы из KiCad в сборке SOLIDWORKS — отдельный документ, и PDM помнит, из какой версии проекта KiCad он получен. Подключение нового CAD — это новый адаптер, а не изменение ядра.

## 3. Серверный архив и локальный кэш

Клиент обращается только к API сервера. Архив не раздаётся как сетевая папка, прямого доступа к БД и хранилищу файлов у пользователей нет. В БД хранятся версии и связи, содержимое файлов лежит отдельно.

- **Архив** хранит неизменяемое содержимое по хешу SHA-256. Разные версии с одинаковым содержимым ссылаются на один объект. Подходят и диск сервера, и S3-совместимое хранилище; в текущем стенде уже есть MinIO, менять его не требуется.
- **Кэш** на компьютере конструктора — неизменяемые скачанные версии. Повторное открытие докачивает только недостающее.
- **Рабочая папка** — файлы с исходными именами и относительными путями, разложенные из кэша. CAD работает только с ней, не по сети. Правка в рабочей папке не портит кэш и не затирается при повторном открытии без предупреждения.

При открытии клиент проверяет, что CAD загрузил компоненты именно из рабочей папки и именно нужных версий. Совпадения имён недостаточно: уже открытая одноимённая модель или конфликт версий одного компонента дают понятное сообщение, а не тихую подмену.

## 4. Блокировки и сдача

**Защита от правки без надстроек.** Файлы, не взятые в работу, лежат в рабочей папке с атрибутом «только для чтения». Любой CAD откажется их перезаписать. «Взять в работу» снимает атрибут только после того, как сервер подтвердил блокировку. Это одинаково работает в SOLIDWORKS, КОМПАС и KiCad и не требует перехвата команд CAD.

1. **Взять в работу.** Сервер резервирует один документ целиком, а не дерево сборки. Двое могут менять разные детали одной сборки, но не одну деталь. Для изменения состава берётся в работу сама сборка.
2. **Создать новый документ.** До первой сдачи он черновой, виден только автору и правится без блокировки.
3. **Сдать.** Адаптер читает ссылки из сохранённых файлов. Сервер проверяет блокировки, исходные версии и наличие зависимостей. Затем записывает недостающие объекты в архив и одной транзакцией БД публикует версии и привязки. При сбое не появляется частичный комплект, старый остаётся доступен, локальные правки и блокировки сохраняются.
4. **Обновить зависимость явно.** Новая версия детали не меняет существующие сборки. Чтобы сборка использовала её, сборку берут в работу и сдают заново. Новая привязка — это новая версия сборки, даже если байты файла не изменились.

Опубликованные версии не исправляются вручную: исправление — новая сдача. Служба работает под отдельной учётной записью, рабочим ролям БД запрещены изменение и удаление опубликованных версий. БД и архив резервируются согласованно.

## 5. Клиент сейчас, надстройки потом

Первые два этапа работают через **отдельный клиент PDM** — настольное приложение Windows с графическим интерфейсом и командной строкой (стек — в [architecture.md](architecture.md)): поставить на учёт, открыть версию, взять в работу, сдать, найти, посмотреть «где применяется», выгрузить комплект. Этого достаточно для всех трёх CAD.

**Надстройки SOLIDWORKS и КОМПАС** — следующий этап и вопрос удобства. Они дают те же команды прямо из CAD и карточку документа. Карточка — это представление открытого документа, а не форма ввода: правка в ней записывает значение в свойства открытого файла, штатное окно свойств CAD видит то же значение. Отдельной редактируемой копии свойств в БД нет и тогда.

## 6. Текущий стенд и путь к целевой модели

Текущий стенд принимает **ZIP-снимки каталогов** под отдельной карточкой изделия в PostgreSQL и MinIO и восстанавливает их с проверкой хешей. Он не проверяет замкнутость комплекта, не фиксирует версии отдельных зависимостей и не поддерживает несколько пользователей и блокировки. Это исходная точка; правила и результаты стенда — в [описании пилота](pilot.md).

Порядок перехода (подробно — раздел 11 [ТЗ](pdm-spec.md)):

1. **Ядро и SOLIDWORKS.** Документы, версии, зависимости, блокировки, кэш и клиент. Первый шаг — проверить чтение ссылок на одном замкнутом комплекте с подсборкой, общей деталью, двумя конфигурациями и чертежами. Для АИРТ.467124.016 сначала нужно получить две отсутствующие детали или выбрать другой комплект. Исходные папки не изменяются.
2. **КОМПАС и KiCad.** Новые адаптеры и связь через STEP без изменения ядра.
3. **Процессы**, по важности: согласование и нормоконтроль по версиям; спецификация по ЕСКД из зафиксированной конфигурации и выпуск с литерой и номером изменения; извещения об изменении; надстройки SOLIDWORKS и КОМПАС с карточкой; веб-просмотр для производства и закупок (раздел 10 [ТЗ](pdm-spec.md)).

Дерево CAD не равно утверждённой спецификации. Внутренние версии появляются при сдаче; официальная ревизия — только при выпуске конкретного комплекта, а изменение выпущенного комплекта — только через извещение об изменении.
